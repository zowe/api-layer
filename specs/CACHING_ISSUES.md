### [#4512](https://github.com/zowe/api-layer/issues/4512) — Detection of failed services during routing

- **State:** open | **Created:** 2026-03-12 | **Labels:** bug, new

**Problem:**
`NettyRoutingFilterApiml` (`gateway-service/src/main/java/org/zowe/apiml/gateway/config/NettyRoutingFilterApiml.java`) wraps only `ConnectException` into `ServiceNotAccessibleException`, which `GatewayExceptionHandler` maps to HTTP 503. All other exceptions — including TLS/certificate failures (`SSLException`) — are re-thrown as-is and hit the generic `Exception` handler returning HTTP 500. Furthermore, the debug message in the handler (`"A service is not available at the moment to finish request %s: %s"`) logs only `ex.getMessage()`, discarding the root cause chain.

**Proposed Solution:**

1. **Narrow the 503 condition** — only `ConnectException` (TCP connection refused/timeout) and `NoRouteToHostException` represent a genuinely unreachable service. Certificate failures (`SSLHandshakeException`, PKIX path exceptions wrapped inside `SSLException`) mean the service is reachable but incorrectly configured, and should result in 500 with a clear TLS error message. Widen `NettyRoutingFilterApiml.filter()` to classify exceptions explicitly:

   ```java
   .onErrorResume(e -> {
       Throwable root = unwrapCause(e);
       if (root instanceof ConnectException || root instanceof NoRouteToHostException) {
           return Mono.error(new ServiceNotAccessibleException("...", e));
       }
       if (root instanceof SSLHandshakeException || isCertificateException(root)) {
           return Mono.error(new ServiceTlsException("TLS handshake failed: " + root.getMessage(), e));
       }
       return Mono.error(e);  // keep other errors as 500
   })
   ```

2. **Add `ServiceTlsException`** (new exception class) and register a dedicated handler in `GatewayExceptionHandler` that returns 500 with a human-readable TLS error message — distinct from the generic 500 catch-all.

3. **Improve the debug log** — change the `handleServiceNotAccessibleException` method to log the full cause chain at `DEBUG` level:

   ```java
   log.debug("Service unavailable for request {}: {}", exchange.getRequest().getURI(), ex.getMessage(), ex);
   ```

4. **Files to change:**
   - `gateway-service/.../config/NettyRoutingFilterApiml.java` — exception classification
   - `gateway-service/.../controllers/GatewayExceptionHandler.java` — new handler + improved log
   - New class `gateway-service/.../exceptions/ServiceTlsException.java`

**Senior Engineer Review:**

The direction is correct but the proposed `unwrapCause()` helper must walk the full exception chain recursively, not just check the immediate cause — Netty often wraps `ConnectException` several levels deep inside a `ClosedChannelException` or `ReactorNetty` wrapper. The `isCertificateException()` predicate must be tested against real Netty SSL exception shapes, as the PKIX failure message text varies between JVM versions.

The `ServiceTlsException` introducing a new 500-level class is sound, but its handler should log at `WARN` not `DEBUG` — a TLS misconfiguration toward a downstream service needs operator visibility, unlike a transient 503.

No tests were proposed. The existing `NettyRoutingFilterApimlTest` has acceptance-level tests for the 503 path (e.g., `allInstancesAreUnavailable()`) but nothing that exercises the new TLS-exception branch or the improved log output. Required test additions:

- **Unit test in `NettyRoutingFilterApimlTest`**: add a `@Nested class GivenTlsFailure` that creates a mock `super.filter()` returning `Mono.error(new SSLHandshakeException("PKIX path building failed"))` and asserts `ServiceTlsException` is produced (not `ServiceNotAccessibleException`).
- **Unit test**: a `ConnectException` wrapped inside a `RuntimeException` (Netty wrapping pattern) must still resolve to 503, verifying the recursive unwrap.
- **Unit test in `GatewayExceptionHandlerTest`**: assert that `ServiceTlsException` is mapped to HTTP 500 with a non-empty JSON body containing the TLS message key, distinct from the generic catch-all body.
- **Update `GatewayExceptionHandlerTest`**: add verification that the `DEBUG` log for `handleServiceNotAccessibleException` now includes the full stack trace (use a `ListAppender` or Logback `TestAppender`).

### [#4511](https://github.com/zowe/api-layer/issues/4511) — Sticky session and HA

- **State:** open | **Created:** 2026-03-12 | **Labels:** bug, new

**Problem:**
`DeterministicLoadBalancer` (`gateway-service/src/main/java/org/zowe/apiml/gateway/loadbalancer/DeterministicLoadBalancer.java`) selects exactly one instance in `chooseOne()` by filtering the full `serviceInstances` list to only the cached `instanceId`. If that instance is unhealthy but still in the Eureka registry, the filtered list contains only the failing instance and every request fails until deregistration.

**Proposed Solution:**

1. **Return a prioritised list instead of a singleton.** Change `filterInstances()` so that, when a sticky instance is known, it returns a list with the preferred instance first followed by all remaining healthy instances. Spring Cloud Gateway's built-in retry filter will then automatically fall back to the next entry in the list on a connection failure.

   ```java
   // Instead of:
   .filter(i -> instanceId.equals(i.getInstanceId())).findAny().orElse(serviceInstances.get(0))

   // Do:
   List<ServiceInstance> ordered = new ArrayList<>();
   serviceInstances.stream()
       .filter(i -> instanceId.equals(i.getInstanceId()))
       .findFirst()
       .ifPresent(ordered::add);
   serviceInstances.stream()
       .filter(i -> !instanceId.equals(i.getInstanceId()))
       .forEach(ordered::add);
   return ordered;   // sticky instance first, others as fallback
   ```

2. **Update the cache entry on fallback.** When a retry succeeds on a different instance, update the `LoadBalancerCache` to store the new instance, so future requests stick to the working one. This can be done in a `GatewayFilter` that runs after routing and detects which instance was ultimately used (the `GATEWAY_LOADBALANCER_RESPONSE_ATTR` exchange attribute).

3. **Files to change:**
   - `gateway-service/.../loadbalancer/DeterministicLoadBalancer.java` — `filterInstances()` and `chooseOne()`
   - Optionally a new post-routing filter to update the cache on successful retry

**Senior Engineer Review:**

The ordered-list approach is correct, but there is a subtle interaction with the retry filter that must be addressed explicitly: the gateway's `RoutingConfig` configures **5 retries on 503 only** (`statuses: SERVICE_UNAVAILABLE`). Returning a multi-instance list from the load balancer alone is not enough — Spring Cloud Gateway's `RetryGatewayFilter` re-invokes the load balancer on each retry, which means `DeterministicLoadBalancer.get()` will be called again and will again return the same preferred instance first (since the cache still points to it). The cache entry for the failed instance must be cleared on the first failure so that the second call to `get()` does not re-prioritise a known-dead instance. This invalidation should happen in `NettyRoutingFilterApiml.filter()` when it catches `ConnectException`, before throwing `ServiceNotAccessibleException`.

The "update cache on fallback" idea via `GATEWAY_LOADBALANCER_RESPONSE_ATTR` is reasonable but the attribute name in Spring Cloud Gateway is `LoadBalancerUriTools.ORIGINAL_INSTANCE_ATTR` — confirm the actual attribute name used by the version of Spring Cloud Gateway in the project before implementing.

The existing tests in `DeterministicLoadBalancerTest` all assert `assertEquals(1, chosenInstances.size())` for the sticky path — after this fix, those assertions must be updated to `assertEquals(2, ...)` with an ordering assertion instead. Specifically:

- **Update `whenInstanceExists_thenUpdateList()`** in both cookie and header nested classes: assert the returned list has size 2, first element is `"instance1"`, second is `"instance2"`.
- **New test `whenPreferredInstanceIsUnavailable_thenFallbackInstanceIsSecond()`**: given a sticky cache record for `"instance1"` and a `ConnectException` thrown during routing, assert that after clearing the cache the next `get()` call returns both instances without a preference.
- **New test `whenCacheIsCleared_thenNextCallPicksAny()`**: simulate the two-request sequence — first call with failing instance1, cache delete triggered, second call returns unordered list.
- The `whenInstanceDoesNotExist_thenUpdatePreference()` test currently returns size 1 with a fallback to `instance1` — verify that with the ordered-list change it now returns size 2 in correct order.

### [#4510](https://github.com/zowe/api-layer/issues/4510) — Unnecessary call of caching service during routing

- **State:** open | **Created:** 2026-03-12 | **Labels:** bug, new

**Problem:**
In `DeterministicLoadBalancer.get()`, the call to `cache.retrieve(user, serviceId)` is made whenever a user principal can be extracted from the request token — regardless of whether the target service has sticky-session routing enabled (`apiml.lb.type=authentication`). The `shouldIgnore()` check that guards against stickiness runs *after* the cache call, not before it.

**Proposed Solution:**

1. **Check the `apiml.lb.type` metadata before touching the cache.** The service metadata is available on every `ServiceInstance` in the list returned by `delegate.get(request)`. Move the metadata guard to be the first thing evaluated:

   ```java
   return delegate.get(request)
       .flatMap(serviceInstances -> {
           // Guard first — no metadata, no cache call
           if (!isStickySessionEnabled(serviceInstances)) {
               return just(checkInstanceIdHeader(serviceInstances, request.getContext()));
           }
           return getSub(request.getContext())
               .flatMap(user -> user.isEmpty()
                   ? empty()
                   : cache.retrieve(user, serviceId).onErrorResume(t -> Mono.empty()))
               ...
       });
   ```

2. **Also guard by `X-InstanceId` header early** — if the header is present, use it directly without a cache call; this is already partially handled by `shouldIgnore()` but needs to be promoted before `getSub()`.

3. **Files to change:**
   - `gateway-service/.../loadbalancer/DeterministicLoadBalancer.java` — reorder the guard and cache-retrieval logic in `get()`

**Senior Engineer Review:**

The problem description is accurate, but the proposed fix is incomplete. Looking at `DeterministicLoadBalancer.get()`, the `shouldIgnore()` check at line 256 already returns `true` when the service metadata does not have `apiml.lb.type=authentication` — but it runs inside the `flatMapMany(cacheRecord -> filterInstances(...))` stage, *after* the cache has already been retrieved. The metadata is available from the first element of `serviceInstances` earlier in the chain, before `getSub()` is called, so the fix is to read metadata from the supplier's result and short-circuit before `getSub()`.

The `X-InstanceId` header path is handled in `checkInstanceIdHeader()` / `shouldIgnore()`, but `shouldIgnore()` also calls `getInstanceId()` which reads the header — this already happens before the sticky session logic. The real regression target is only the `cache.retrieve()` call for non-sticky services that have an authenticated user.

The `LoadBalancerCache.cachingServiceAvailability()` is called on every `retrieve()` and `store()`, which issues an `eurekaClient.getApplication("cachingservice")` call. This is a second hidden I/O operation that the fix should also eliminate by short-circuiting before `getSub()`.

No tests were proposed. The existing test `whenServiceDoesNotHaveMetadata_thenUseDefaultList()` and `whenServiceDoesNotUseSticky_thenUseDefaultList()` both still call `when(lbCache.retrieve(...)).thenReturn(...)` — after the fix, those mocks should **not** be invoked at all. Required test additions:

- **Update `whenServiceDoesNotHaveMetadata_thenUseDefaultList()`** and **`whenServiceDoesNotUseSticky_thenUseDefaultList()`**: add `verify(lbCache, never()).retrieve(anyString(), anyString())` to confirm the cache is not touched.
- **New test `whenStickyDisabled_andCachingServiceDown_thenRequestSucceeds()`**: configure `lbCache.retrieve()` to throw a `CachingServiceClientException`, set metadata to non-sticky, and assert the full instance list is returned without error — confirming resilience to caching service failures for non-sticky services.
- **New test `whenInstanceIdHeaderPresent_thenCacheNotCalled()`**: set `X-InstanceId` header and a valid token, assert `lbCache.retrieve()` is never called.

**Senior Engineer Review:**

The proposal is directionally right but underestimates scope. ### [#4451](https://github.com/zowe/api-layer/issues/4451) — Salt in caching service is represented as String even it contains binary data

- **State:** open | **Created:** 2026-01-09 | **Labels:** bug, Priority: High

**Problem:**
In `ApimlAccessTokenProvider` (`zaas-service/src/main/java/org/zowe/apiml/zaas/security/service/token/ApimlAccessTokenProvider.java`), `storeSalt()` and `initializeSalt()` convert the raw 16-byte salt to/from `String` using `new String(byte[])` (platform default charset). If any byte is a control character or maps to a multi-byte sequence, the resulting string is shorter than 16 characters and `getSalt()` returns fewer bytes than expected, weakening the hash.

**Proposed Solution:**

1. **Store and retrieve the salt as Base64.** Change `storeSalt()` to encode with `Base64.getEncoder().encodeToString(salt)` and `initializeSalt()` to decode with `Base64.getDecoder().decode(value)`. The salt is always stored and returned as a `byte[]`; it is never used as a String internally.

   ```java
   // Store:
   cachingServiceClient.create(new CachingServiceClient.KeyValue(
       "salt", Base64.getEncoder().encodeToString(newSalt)));

   // Load:
   byte[] salt = Base64.getDecoder().decode(keyValue.getValue());
   ```

2. **Remove `getSalt()` returning `String.getBytes()`** — the method should return `byte[]` directly from the decoded value, never going through a `String` representation.

3. **Add a migration path** — on first startup after the fix, if the stored salt cannot be Base64-decoded (i.e., it was stored in the old raw-bytes format), generate a new salt and store it. Log a warning that a new salt was created and all existing PAT hashes are now invalid (users will need to re-authenticate).

4. **Files to change:**
   - `zaas-service/.../security/service/token/ApimlAccessTokenProvider.java` — `storeSalt()`, `initializeSalt()`, `getSalt()`
   - Add a unit test covering a salt containing byte values 0x00–0x1F

**Senior Engineer Review:**

The Base64 fix is correct and necessary. However, the `@BeforeEach` in `ApimlAccessTokenProviderTest` currently uses `new String(ApimlAccessTokenProvider.generateSalt())` to pre-populate the mock — this will continue to work for the current tests because the mock bypasses the actual read/decode path, but it means the test does not exercise the Base64 decode round-trip at all. After the fix, the `@BeforeEach` mock must be updated to return a Base64-encoded string: `Base64.getEncoder().encodeToString(ApimlAccessTokenProvider.generateSalt())`.

The migration concern is real but the "catch `IllegalArgumentException` from Base64.getDecoder().decode()" approach is fragile — a legacy raw-byte salt that happens to be valid Base64 by coincidence would be silently accepted as a valid salt but produce a different byte sequence than was originally stored. A better migration is to attempt decode, and if the decoded length ≠ 16 bytes or the Base64 decode throws, regenerate unconditionally and log a clear message.

Required test additions or updates in `ApimlAccessTokenProviderTest`:

- **Update `@BeforeEach`**: change `new String(generateSalt())` to `Base64.getEncoder().encodeToString(generateSalt())` in the mock setup so all existing tests use the new format.
- **Update `givenNoSaltInCache_whenInitializing_thenCreateNewOne()`**: add a `verify` that `cachingServiceClient.create()` is called with a value that is valid Base64 and decodes to exactly 16 bytes.
- **New test `givenSaltWithControlBytes_whenStored_thenRoundTripIsLossless()`**: construct a 16-byte array where bytes 0–5 are control characters (0x00–0x05), store via `storeSalt()`, decode via `initializeSalt()`, and assert `Arrays.equals(original, decoded)`.
- **New test `givenLegacySaltFormat_whenInitializing_thenRegeneratesAndLogs()`**: mock the cache to return a raw-byte string that is not valid Base64, assert a new salt is generated and stored, and assert a `WARN` log message is emitted.
- **New test `givenBase64SaltInCache_whenGetSalt_thenReturns16Bytes()`**: end-to-end round-trip asserting `getSalt().length == 16` regardless of byte content.

### [#4427](https://github.com/zowe/api-layer/issues/4427) — Caching service health endpoint

- **State:** open | **Created:** 2025-12-12 | **Labels:** enhancement, Priority: Medium

**Problem:**
The caching-service's `/application/health` endpoint (Spring Boot Actuator) reports `UP` based on application-level checks but has no visibility into JGroups/Infinispan cluster connectivity. A caching-service node can be running but isolated from the cluster, silently causing split-brain.

**Proposed Solution:**

1. **Implement a custom `HealthIndicator` bean** in the caching-service that queries the Infinispan `EmbeddedCacheManager` for cluster membership:

   ```java
   @Component
   public class InfinispanHealthIndicator implements HealthIndicator {
       @Autowired(required = false)
       private EmbeddedCacheManager cacheManager;

       @Override
       public Health health() {
           if (cacheManager == null) return Health.up().withDetail("mode", "standalone").build();
           ClusterExecutor executor = cacheManager.executor();
           int clusterSize = cacheManager.getMembers().size();
           int expectedSize = /* from config: infinispan.cluster.expectedNodes */ 1;
           if (clusterSize < expectedSize) {
               return Health.down()
                   .withDetail("clusterSize", clusterSize)
                   .withDetail("expectedSize", expectedSize)
                   .build();
           }
           return Health.up().withDetail("clusterSize", clusterSize).build();
       }
   }
   ```

2. **Add `infinispan.cluster.expectedNodes` configuration property** (default 1 = standalone) so operators can define the minimum required cluster size for the node to be considered healthy.

3. **Expose the view** — log a `WARN` when cluster membership drops below the expected size, and log `INFO` when it recovers.

4. **Files to change:**
   - New `caching-service/.../health/InfinispanHealthIndicator.java`
   - `caching-service/src/main/resources/application.yml` — add `infinispan.cluster.expectedNodes`

   ```java
               return cachingServiceClient.read("salt").getValue();
           }
       }
   }
   ```

- **State:** open | **Created:** 2023-10-10 | **Labels:** bug, Priority: Medium, V3

Spring Boot's graceful shutdown (`server.shutdown: graceful`) is not configured, so the embedded Netty server does not wait for in-flight requests nor issues a `SIGTERM` to trigger JVM exit.

**Proposed Solution:**

1. **Enable Spring Boot graceful shutdown** in `gateway-service/src/main/resources/application.yml`:

   ```yaml
   server:
     shutdown: graceful
   spring:
     lifecycle:
       timeout-per-shutdown-phase: 30s
   ```

   This instructs the embedded server to stop accepting new connections and wait up to 30 seconds for active requests to complete before the Spring context closes.

2. **Deregister from Eureka before stopping the server.** Implement a `SmartLifecycle` bean with a low `getPhase()` value that calls `eurekaClient.shutdown()` as the first shutdown step, so the Discovery service removes the Gateway from its registry before it stops accepting connections.   
   ```java
   @Component
   public class EurekaDeregistrationLifecycle implements SmartLifecycle {
       @Override
       public int getPhase() { return Integer.MIN_VALUE; }  // run first on stop

       @Override
       public void stop() {
           eurekaClient.shutdown();
           running = false;
       }
   }
   ```

If the Gateway does not shut down within 30s, Spring will force-close it regardless, potentially dropping in-flight requests. Document this dependency explicitly.
